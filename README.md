# Findr

Search across your work apps (Google Drive, Slack, Gmail, …) from one search bar, and ask questions that are answered with citations back to the original sources. Each user only sees content they can already see in the source app.

Design docs live in [architecture/](architecture/). Current status: **the core works end to end on demo data**: ingestion, hybrid search with filters, a search-quality evaluation, and streamed AI answers with citations. Real connectors (Drive, Slack, Gmail) come next.

## What it does

- **Hybrid search**: keyword search (exact names, codes like `INC-2041`) and meaning search (embeddings, so "days off" finds the vacation policy) run together and are merged with weighted Reciprocal Rank Fusion. Filters can be typed (`source:demo type:email from:esi in:#sales after:2026-02-01`) or picked as chips.
- **AI answers with citations**: ask a question, get an answer streamed word by word with `[1]` `[2]` markers that link to the sources. Follow-up questions keep the context (they're rewritten into standalone searches). If the sources don't say, it says it couldn't find it.
- **Permissions everywhere**: every search and every answer is filtered by the user's access inside SQL, before ranking. Restricted demo documents never appear, in any mode.
- **Safe answers**: answers are rendered as text with a tiny Markdown subset: no images, and links only to cited sources, so an injected instruction in a document can't exfiltrate data.

## Search quality (evaluation)

53 golden questions over the demo data ([backend/eval/golden.json](backend/eval/golden.json)): 47 answerable (facts, paraphrases, filters) plus restricted and unanswerable ones. Real embeddings (`gemini-embedding-2`), Recall@10 / MRR / nDCG@10:

| Mode     | Recall@10 | MRR   | nDCG@10 |
| -------- | --------- | ----- | ------- |
| Keyword  | 0.908     | 0.812 | 0.832   |
| Semantic | 1.000     | 0.989 | 0.988   |
| Hybrid   | 1.000     | 0.950 | 0.960   |

No permission leaks. Two findings along the way: switching keyword matching from "all words" to "any word, ranked" raised keyword Recall@10 from 0.38 to 0.91, and weighting keyword ranks at 0.25 in the fusion (found with `--sweep`) lifted hybrid MRR from 0.91 to 0.95. On this small dataset meaning-only search ranks slightly better still; hybrid keeps keyword search as a safety net for exact codes and for when embeddings are unavailable. CI runs the same eval with a fake embedder on every push.

## Layout

```
backend/     Fastify API + background worker (TypeScript)
  src/api/         routes, plugins, server entry point
  src/auth/        access tokens, refresh-token rotation, Google sign-in, principals
  src/db/          Drizzle schema + database client (PGlite or Postgres)
  src/connectors/  connector interface + the demo connector (fictional company "Tamarind Labs")
  src/ingestion/   normalize, chunk, embed, index, sync engine, job scheduler
  src/search/      query parser, hybrid SQL, ranking
  src/ai/          chat model client, prompt, citations, answer pipeline
  src/connections/ connection management
  src/worker/      BullMQ worker that runs sync jobs when REDIS_URL is set
  eval/            golden questions, metrics and the eval runner
  migrations/      SQL generated by drizzle-kit
  tests/           Vitest tests (run against in-memory PGlite)
frontend/    React + Vite web app
architecture/ design documents
```

## Run it locally (no Docker)

Requires Node 22+ and pnpm.

```sh
pnpm install
cp backend/.env.example backend/.env
pnpm --filter backend gen:keys      # paste the two printed lines into backend/.env
pnpm dev                            # API on :3000, web app on http://localhost:5173
```

The database is [PGlite](https://pglite.dev), real Postgres compiled to WebAssembly, stored in `backend/.data/`. Nothing to install. Delete that folder to reset.

With `DEV_LOGIN_ENABLED=true` you can sign in with any email address. To use Google sign-in, set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` (see `.env.example`).

Then open **Connections → Add demo data**, go back to **Search** and ask something like _"When will Harbor get the route optimizer, and did the date change?"_.

### Free tier: one Gemini key

Set `GEMINI_API_KEY` (free, from [Google AI Studio](https://aistudio.google.com) → Get API key). It's used for both embeddings (`gemini-embedding-2`, 768 dimensions) and answers (`gemini-flash-lite-latest`, falling back to `gemini-flash-latest` when busy). Without a key everything still runs, with a fake embedder and a fake answer model, which is what the tests and CI use.

Free-tier notes: requests are rate-limited client-side; a search waits at most 4 s for its embedding and otherwise falls back to keyword results; answers switch models when one is overloaded or silent for 6 s. On the free tier Google may use requests to improve its products, so it suits the demo data rather than real private email.

### How syncing runs

| Setting              | Development (default)                                             | Production                                         |
| -------------------- | ----------------------------------------------------------------- | -------------------------------------------------- |
| `REDIS_URL` unset    | Syncs run in the background of the API process                    | Not allowed                                        |
| `REDIS_URL` set      | API queues jobs in BullMQ; run `pnpm --filter backend dev:worker` | Same; the worker needs `DATABASE_URL=postgres://…` |
| No `GEMINI_API_KEY`  | Fake embedder and answer model                                    | Not allowed                                        |
| `GEMINI_API_KEY` set | Gemini embeddings and answers                                     | Same                                               |

## Common commands

| Command                                     | What it does                                         |
| ------------------------------------------- | ---------------------------------------------------- |
| `pnpm dev`                                  | Run API and web app with hot reload                  |
| `pnpm test`                                 | Run all tests                                        |
| `pnpm lint` / `pnpm typecheck`              | Static checks (CI runs these on every push)          |
| `pnpm format`                               | Format all files with Prettier                       |
| `pnpm --filter backend eval`                | Search-quality eval with real embeddings (needs key) |
| `pnpm --filter backend eval --fake --sweep` | Eval with the fake embedder; compare fusion weights  |
| `pnpm --filter backend db:generate`         | After editing `schema.ts`: write a migration         |
| `pnpm --filter backend db:migrate`          | Apply migrations to `DATABASE_URL`                   |
